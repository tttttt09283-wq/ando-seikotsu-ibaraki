# テスト計画 — AND GROUP MANAGEMENT SYSTEM

設計案 0.2（**未承認**。2026-11-05 の回答を反映）。

## 1. テストの層

| 層 | ツール | 対象 |
|---|---|---|
| 単体 | Vitest | 日付計算（議事録期限・有給の有効期限）、残数計算、年5日判定、CSV検証、権限判定の純粋関数 |
| データベース | pgTAP（`supabase test db`） | **RLS・RPC関数・制約**（承認順序・自己承認・排他・二重減算）。ルールの最終防衛線を直接検証 |
| 結合 | Vitest＋ローカルSupabase | Server Action → RPC → DB の一連の流れ、同時実行 |
| E2E | Playwright（PC・スマホ幅） | 申請〜承認〜残数反映、議事録提出、ダッシュボードの遷移 |
| 手動 | 受け入れテスト | 全7院の院長・GM・社長による操作確認（PHASE 10） |

- テストデータは架空の7院・各院5〜8名・全役職・複数店舗所属者を含むシードで作る（**実データは使わない**）。
- 時刻に依存するテストは「現在時刻」を固定して実行する。

## 2. 必須検証項目（指示書 §17）

| No | 検証内容 | 主な層 | 手順・期待結果 |
|---|---|---|---|
| T-01 | 社長以外が有給を最終承認できない | DB・E2E | GM・BM・院長・スタッフで `decide_approval_step(approve)` を呼ぶ → すべて権限エラー。社長のみ成功 |
| T-02 | 院長が自院スタッフの振休を承認できる | DB・E2E | A院院長がA院スタッフの振休を承認 → 取得予定に反映・利用可能残数が減る |
| T-03 | 院長が他院の振休を承認できない | DB | A院院長がB院スタッフの振休を承認 → 権限エラー。RLSでB院の申請が一覧にも出ない |
| T-04 | 自己承認を防止できる | DB・E2E | 有給・アルバイト勤務・振休変更・規定で、申請者＝承認者の承認 → 拒否。**例外：院長本人の振休は本人承認が成功し、「本人承認」の印とGM・社長への通知が残る**。院長がほかの役職の本人申請（例：自分の有給）を承認 → 拒否 |
| T-05 | GM確認前の振休勤務変更を最終承認できない | DB | 社長がステップ2を承認（ステップ1が pending）→ 順序エラー。GM確認後は成功 |
| T-06 | 社長以外がアルバイト勤務を最終承認できない | DB | GM・院長で承認 → 権限エラー |
| T-07 | 休暇残数が正しく計算される | 単体・DB | 付与・取得済み・予定・申請中・調整・失効を組み合わせた表（§3）で、各表示値が期待値と一致 |
| T-08 | 取消時に残数が正しく戻る | DB | 承認済み予定を取消 → 利用可能残数が元に戻る。取消を2回実行しても1回分だけ戻る |
| T-09 | 有給の期限・繰越が正しく処理される | 単体・DB | 2年の有効期限、期限の早い付与から割り当て、期限当日は使用可・翌日は不可、失効の記録 |
| T-10 | 議事録期限が暦日3日後になる | 単体・DB | 下表の日付で期限が「開催日＋3日 23:59:59 JST」（土日祝・月末・年末年始・うるう年） |
| T-11 | 期限超過後の提出を正しく記録できる | DB・E2E | 期限の1秒後に提出 → 「提出済み（期限超過）」、提出日時を保持、期限超過の記録が消えない |
| T-12 | 複数店舗所属者の権限が正しい | DB | A院院長＋B院スタッフの人：A院の振休は承認可・B院は不可、B院では自分の情報のみ |
| T-13 | 7院のデータが不正に混在しない | DB | 7院それぞれの院長・スタッフで全テーブルを SELECT → 自院（と自分）の行だけ。店舗IDを書き換えた INSERT/UPDATE は拒否 |

## 3. 残数計算のテストケース（T-07〜T-09）

| ケース | 前提 | 期待 |
|---|---|---|
| 基本 | 付与10日、取得済み2、予定1、申請中1 | 現在残数8、取得予定反映後7、申請中1（参考6） |
| 調整 | 上記＋調整＋0.5（理由あり） | 現在残数8.5 |
| 2つの付与 | 前年残4日（期限近い）＋今年11日、1日取得 | 前年分から割り当て、前年残3 |
| 期限をまたぐ申請 | 前年分の期限の翌日に取得予定 | 今年分から割り当て |
| 失効 | 前年分が期限切れ、残2日 | 失効2日を記録、現在残数から除外 |
| 同時承認 | 残1日に対し、別々の1日の申請2件を同時に承認 | 1件だけ通常承認、もう1件は残数不足の再確認が必要になる（マイナスにならない） |
| 二度押し | 同じ idempotency_key で承認2回 | 取得行は1件だけ |
| 半日 | 半日制度ON、0.5日×2回 | 1.0日減少、年5日に1.0日算入 |
| 時間単位 | 時間単位制度ON、3時間 | 残数は換算で減少、年5日には算入しない |
| 移行残高 | CSVで残8日（source=migration） | 付与として表示、「移行時点の残数」と表示 |

## 4. 議事録期限のテストケース（T-10・T-11）

| 開催日 | 期限（JST） | 23:59:59 に提出 | 翌 0:00:00 に提出 |
|---|---|---|---|
| 2026-11-05（木） | 2026-11-08 23:59:59 | 期限内 | 期限超過 |
| 2026-11-27（金） | 2026-11-30 23:59:59 | 期限内 | 期限超過 |
| 2026-12-30（水） | 2027-01-02 23:59:59 | 期限内 | 期限超過 |
| 2027-02-26（金） | 2027-03-01 23:59:59 | 期限内 | 期限超過 |
| 2028-02-27（日） | 2028-03-01 23:59:59 | 期限内 | 期限超過 |

- サーバーのタイムゾーンをUTCにして実行しても結果が同じこと。
- 「開催日 22:00 終了 → 72時間後」ではないこと（2026-11-05 22:00 開催でも期限は 11-08 23:59:59）。

| ケース | 期待 |
|---|---|
| 付与10日・期間内に全日3＋半日2回 | 取得済み4.0、残り必要1.0 |

## 6. セキュリティ検証

| 項目 | 内容 |
|---|---|
| RLS網羅 | 全テーブルで RLS が有効か（ポリシー無しのテーブルが無いか）を自動チェック |
| 直接更新の禁止 | 一般ユーザーのJWTで `leave_requests.status`・`approval_steps`・`leave_usage` を直接 UPDATE → 拒否 |
| 監査ログ | 社長を含む全ユーザーで `audit_logs`・`approval_events` の UPDATE/DELETE → 拒否 |
| 退職者 | 退職処理後のアカウントでログイン・API呼び出し → 拒否。進行中の承認に「承認者不在」通知 |
| 入力値 | 日付・数値・文字数の範囲外、HTML/スクリプト文字列 → 拒否または無害化 |
| サービスロールキー | ブラウザに送られるバンドル・レスポンスに含まれないこと |
| 承認者本人確認 | ログインから一定時間経過後の承認 → 再ログインを要求 |
| 通知の重複 | 日次ジョブを2回実行 → 通知は1回 |
