## 1. 目的と目指す状態

社内規定・院内会議・休暇管理・アルバイト申請・承認フロー・業務進捗を一元管理する。

| ID | 目指す状態 | 主な機能 |
|---|---|---|
| G-1 | 院長が自院の管理業務を自律的に遂行できる | 院長ダッシュボード、振休承認、会議・議事録、タスク |
| G-2 | 社長が必要な申請を一画面で承認できる | 社長ダッシュボード（承認キュー） |
| G-3 | GMが全院の状況をリアルタイムで確認できる | GMダッシュボード（KPI・ドリルダウン） |
| G-4 | スタッフが自分の有給・振休残数を確認できる | マイページ（残数・履歴） |
| G-5 | 申請漏れ・報告遅延・残数不足・無断変更を防止できる | 期限通知、残数チェック、状態遷移の制約、監査ログ |

- エリア（BMの担当範囲）は `areas` で管理する（担当の割り当ては未確定：Q-14）。

## 3. 利用者と役職

役職は **社長／GM／BM／院長／一般スタッフ／アルバイト** の6つ。RBAC（役職→権限）で管理する。詳細は [permissions.md](./permissions.md)。

- 1人が複数店舗に所属できる（院ごとに役職が異なってもよい）。
- **自己承認は禁止**。自己承認になる申請は代替承認ルートへ回す（代替承認者は未確定：Q-1）。
- アルバイトの権限は指示書に明記がないため、一般スタッフと同等（自分の情報・規定確認・タスク確認）を初期案とし、休暇申請の可否は未確定（Q-10）。

## 4. 機能要件

### 4.1 認証・権限・店舗（PHASE 2）

| ID | 要件 |
|---|---|
| FR-AUTH-1 | 個人ごとのアカウントでログインする（共有アカウント禁止）。**このシステムでID・PASSを発行**し、POSと同じID・PASSで入れる（Q-7） |
| FR-AUTH-2 | 役職・店舗の組み合わせで閲覧・操作範囲を決める（RBAC＋店舗スコープ） |
| FR-AUTH-3 | 重要操作（承認・残数修正・規定公開など）はサーバー側で認証と権限を再確認する |
| FR-AUTH-4 | 退職者のアカウントを停止できる（データは保持） |
| FR-AUTH-5 | 店舗・エリア・役職・所属をマスタとして管理できる |

### 4.2 休暇残数管理（PHASE 3）

| ID | 要件 |
|---|---|
| FR-LV-1 | 有給休暇・振替休日・代休を別々に管理する |
| FR-LV-2 | スタッフごとに 付与日数／取得済み／承認済み取得予定／申請中／現在残数／取得予定反映後の残数／有効期限／取得履歴 を表示する |
| FR-LV-3 | 有給は付与日（付与年度）単位で管理する |
| FR-LV-4 | 繰越・失効・半日取得・時間単位取得を、会社制度と法令に合わせて設定できる（制度は未確定：Q-3） |
| FR-LV-5 | 残数は付与・取得・調整の履歴から算出する（残数を直接書き換えない） |
| FR-LV-6 | 管理者の残数修正は、理由・修正者・日時を記録する |
| FR-LV-7 | 申請中の日数は確定減算せず、別に表示する |
| FR-LV-8 | 承認済み取得予定は利用可能残数に反映し、二重申請を防ぐ |
| FR-LV-9 | 取消時に残数を整合的に再計算する |
| FR-LV-10 | 残数不足の申請は警告を表示し、通常処理から例外確認へ切り替える |
| FR-LV-11 | 法定の年5日取得義務の対象者を基準日ごとに管理し、未達見込みを通知する |

計算方法の詳細は [leave-management.md](./leave-management.md)。

### 4.3 CSV初期移行（PHASE 3）

| ID | 要件 |
|---|---|
| FR-CSV-1 | 全7院のスタッフ情報をCSVで登録できる |
| FR-CSV-2 | 有給・振休の現在残数をCSVで取り込める |
| FR-CSV-3 | 取り込み前に、重複・不正値・不足項目を検証して結果を一覧表示する（エラーがあれば取り込まない） |
| FR-CSV-4 | 履歴が不明な残数は「移行時点の初期残高」として記録する |
| FR-CSV-5 | 取り込みは社長（または指定の管理者）の明示的な実行で行い、取り込み単位で取り消せる |

### 4.4 有給・振休の申請と承認（PHASE 4）

| ID | 要件 |
|---|---|
| FR-PL-1 | 有給：スタッフまたは院長が申請 → 社長が承認・差戻し・却下 → 取得予定 → 取得実績 |
| FR-PL-2 | 有給の最終承認者は社長のみ。院長とGMは状況を閲覧できる |
| FR-PL-3 | 社長承認前は「承認待ち」と表示する |
| FR-PL-4 | 有給の法的権利を不当に制限しない。時季変更権などの判断は人が行い、システムは自動で却下しない（表現・運用は Q-9） |
| FR-SH-1 | 振休：スタッフ申請 → 所属院長が承認・差戻し・却下 → 取得予定 → 取得実績 |
| FR-SH-2 | 振休の最終承認者は所属院の院長。GMと社長は全院の状況を閲覧できる |
| FR-SH-3 | **院長本人の振休は院長本人が承認できる**（自己承認禁止の例外。本人承認の印を残し、GM・社長に通知）。その他の自己承認になる申請は代替ルートへ（Q-13） |
| FR-SH-4 | 振休は**祝日出勤（祝振替）・公休出勤（振替）**で発生し、**原則その月のうちに取得**。期限切れは失効させずアラート（Q-2） |

### 4.5 アルバイト勤務申請（PHASE 5）

| ID | 要件 |
|---|---|
| FR-PT-1 | 院長申請 → 社長が承認・差戻し・却下 → 勤務予定確定 |
| FR-PT-2 | 申請区分：①シフト作成前の計画申請 ②急な欠員によるヘルプ申請 ③土日祝・平日夜間の繁忙時間帯申請 |
| FR-PT-3 | 希望は**原則シフト確定前まで**。シフト確定後の申請は「例外申請」とし、理由を必須にする（シフト確定日の定義は Q-20） |
| FR-PT-4 | 緊急申請も社長承認が必要（承認前は勤務予定を確定しない） |
| FR-PT-5 | 最終承認者は社長のみ |

### 4.6 振休からアルバイト勤務への変更（PHASE 6）

| ID | 要件 |
|---|---|
| FR-HC-1 | 院長申請 → GM事前確認 → 社長最終承認 → 変更確定 |
| FR-HC-2 | GM確認が終わるまで、社長は最終承認できない（データベースで強制する） |
| FR-HC-3 | 承認前に勤務区分を確定変更できない |
| FR-HC-4 | 実際の勤務実績は申請状態と独立して記録し、法令に従って処理できるようにする（労働時間・割増賃金の扱いは Q-8） |

### 4.7 院内会議・議事録・タスク（PHASE 7）

| ID | 要件 |
|---|---|
| FR-MT-1 | 会議は議事録の正式提出をもって完了とする |
| FR-MT-2 | 提出期限＝会議開催日の3日後の 23:59:59（日本時間 Asia/Tokyo、土日祝を含む暦日）。会議終了時刻からの72時間ではない |
| FR-MT-3 | 議事録の必須項目：店舗・開催日・会議名・参加者・議題・会議内容・決定事項 |
| FR-MT-4 | 決定事項がある場合は、担当者・実施期限・具体的な行動を必須にする |
| FR-MT-5 | 会議ステータス：開催予定／議事録未提出／提出済み／期限超過。期限後の提出は「提出済み（期限超過）」 |
| FR-MT-6 | 決定事項（アクション）の実行状況は会議の完了とは別に管理する |
| FR-MT-7 | 期限の前日・当日・期限超過時に通知する |
| FR-TK-1 | 院長は自院のタスクを管理でき、スタッフは自分のタスクを確認できる（決定事項からのタスク化を含む） |

### 4.8 社内規定（PHASE 8）

| ID | 要件 |
|---|---|
| FR-RL-1 | 規定ごとに 規定番号・規定名・本文・適用対象・施行日・バージョン・承認者・公開状態・改定履歴 を保存する |
| FR-RL-2 | 社長承認後に公開できる |
| FR-RL-3 | スタッフの既読・確認履歴をバージョン単位で記録する |
| FR-RL-4 | 初期規定 001〜005 は「初期案（下書き）」として登録し、会社の正式承認と労務確認が完了するまで施行済みとして扱わない |

初期規定：001 院内会議・議事録提出／002 アルバイト勤務申請／003 振休からアルバイト勤務への変更／004 有給休暇申請・残数管理／005 振替休日取得・残数管理

### 4.9 ダッシュボード（PHASE 9）

| ID | 対象 | 要件 |
|---|---|---|
| FR-DB-1 | GM | 全7院のKPIを一画面に表示（KPIの一覧は [screens.md](./screens.md)）。店舗別・月別・スタッフ別で絞り込み、数値をクリックすると対象データへ遷移する |
| FR-DB-2 | 院長 | 自院の会議予定・議事録期限・未完了タスク・スタッフ別残数・申請状況・振休承認待ち・期限超過業務。スマートフォンで簡単に操作できる |
| FR-DB-3 | 社長 | 承認業務を最優先に表示（有給・アルバイト・振休変更・規定の承認待ち＋全院の状況）。承認画面に申請内容・理由・対象日・対象スタッフ・申請者・関連残数を表示。差戻し・却下は理由必須。承認履歴を保存 |
| FR-DB-4 | BM | 担当エリアの店舗の申請・会議・休暇状況を閲覧 |
| FR-DB-5 | スタッフ | 自分の残数・申請・タスク・未確認の規定 |

### 4.10 通知（PHASE 9）

| ID | 要件 |
|---|---|
| FR-NT-1 | 初期はアプリ内通知のみ（LINE・メールは将来：Q-16） |
| FR-NT-2 | 通知の種類：有給申請受付／社長への承認依頼／振休申請受付／院長への承認依頼／アルバイト勤務申請／GMへの振休変更確認依頼／承認・却下・差戻し／議事録提出期限／議事録期限超過／有給有効期限接近／年5日取得義務未達見込み／社内規定改定 |
| FR-NT-3 | 通知履歴を保持し、同じイベントによる重複通知を防ぐ（イベントキーで一意） |

## 5. 非機能要件

| ID | 区分 | 要件 |
|---|---|---|
| NFR-1 | 対応端末 | PC・スマートフォン（院長・スタッフはスマホ中心）。将来PWA化できる構成 |
| NFR-2 | 言語 | 日本語UI |
| NFR-3 | 日時 | 時刻（timestamp）はUTCで保存し日本時間で表示。暦日（休暇日・会議日）は日付型で保存 |
| NFR-4 | 整合性 | 承認・残数更新はトランザクションで実行。二重承認・二重減算・同時更新を防止 |
| NFR-5 | セキュリティ | 個人認証・RBAC・店舗別アクセス制御（RLS）・操作履歴・自己承認防止・入力値検証・退職者停止・個人情報保護 |
| NFR-6 | 監査 | 監査ログは一般ユーザーが変更・削除できない（追記のみ） |
| NFR-7 | 拡張性 | 店舗数・役職・休暇区分・規定をマスタで追加できる |
| NFR-8 | 可用性 | バックアップ・復旧手順を用意する（[architecture.md](./architecture.md) §8） |
| NFR-9 | 保存期間 | 有給の記録は法定の保存期間を満たす（年次有給休暇管理簿：Q-17） |
| NFR-10 | 性能 | ダッシュボードの表示は通常3秒以内（7院・スタッフ100名規模を想定） |
