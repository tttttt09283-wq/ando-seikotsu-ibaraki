### 3-2 守り方
- **すべての権限確認はサーバー側で行う**：画面のボタンを隠すだけにしない。
  - データベース（Supabase PostgreSQL）の行レベルセキュリティ（RLS）で「見てよい行」を制限
  - 書き込み・承認はサーバー側の処理（Next.js の Server Actions / Route Handlers）を通し、`can(actor, action, resource)` の1か所の関数で判定。承認の状態遷移もここで検査（例：社長承認前に公開できない）
- **所属は期間つき**で持つ（`assignments.valid_from / valid_to`）。異動は旧所属を終了して新所属を追加、兼務は複数行。
- **代理承認**：`delegations`（誰が・誰の・どの権限を・いつからいつまで）。代理で承認した記録には「代理」と元の承認者を残す。
- **退職**：退職日の翌日0時に自動で所属が終了し、ログイン不可。Supabase Auth のアカウントも停止し、セッションを無効化。記録（申請・評価・監査ログ）は消さずに残す。
- 承認者が自分自身の申請を承認することはできない（院長の振替は GM または社長が承認）。

## 4. 技術構成

### 4-1 既存リポジトリの確認結果
| 既存 | 内容 | マニュアルシステムでの扱い |
|---|---|---|
| 予約・会計（直下の HTML＋`api/`） | 静的HTML＋Vercel関数＋Supabase。`clinic_staff` テーブル、`role='admin'`、院ID＋院PASS＋個人PASSのログイン（`lib/pin-auth.js`） | スタッフ台帳とログインを**再利用**（二重管理しない） |
| 本部システム（`hq/`） | 別Vercelプロジェクト、管理者のみ、`hq_docs` | GM向けの全社数値はhqと重ならないように分担。KPIはhqと同じ台帳（`lib/`）を読む |
| カラダ年齢チェック（`body-check/`） | Next.js 16＋Tailwind 4＋TypeScript | 同じ構成を採用（チーム内で実績あり） |

### 4-2 採用する構成
- `manual/` ディレクトリに **Next.js（App Router）＋TypeScript＋Tailwind CSS** で新規作成、**Vercel の別プロジェクト**（Root Directory = `manual`）として公開
- **Supabase**：予約管理と同じプロジェクトを使い、テーブル名の頭に `mn_` を付けて分ける（既存テーブルを壊さない）。SQLは `sql/` に日付つきで追加
- 入力チェック：**zod** でサーバー側・画面側の両方に同じ定義を使う
- テスト：vitest（日付計算・稼働率・権限判定・承認の状態遷移は必ずテストを書く）
- 時刻はすべて `timestamptz` で保存し、期限の計算は **Asia/Tokyo** で行う

### 4-3 検索
- 初期版：PostgreSQL の `pg_trgm`（3文字の部分一致）＋2文字以下の語（「有給」「遅刻」など）は `ILIKE` を併用。言い換え辞書（例：有休→有給、口コミ→クチコミ）をテーブルで持つ
- 検索対象は**公開済み**の版のみ（スタッフ）。管理者は下書きも検索できる
- 将来のAI質問：`pgvector` で公開済みの版だけを索引し、回答には必ず「参照元のルールID・版・改訂日」を表示。根拠が見つからないときは断定せず「GMに確認してください」と案内する。データ構造は初期版から版単位（`mn_doc_versions`）にしておく

### 4-4 個人情報・セキュリティ・バックアップ
- **患者の情報・診療情報・要配慮個人情報は保存しない**（入力欄も作らない。自由記入欄には注意書きを表示）
- スタッフ情報は「氏名・所属・役職・入社日・退職日・雇用区分・ログイン用メール（任意）」だけ。住所・電話番号・マイナンバー・口座は持たない
- 通信は HTTPS のみ、保存は Supabase の暗号化（保存時暗号化）。サービスロールキーはサーバー側の環境変数だけに置く
- **監査ログ**：ルール・申請・評価・KPI・権限の変更はすべて `mn_audit_log`（誰が・いつ・何を・変更前後）に記録。追加のみで、更新・削除はできない（RLSで禁止）
- バックアップ：Supabase の自動日次バックアップ＋週1回の書き出し（社長・GMだけが触れる保管先）。年次有給休暇管理簿は**3年以上**保存。復元手順を運用マニュアルに書き、Phase 8 で一度復元テストをする

## 5. データベース設計

`mn_` 接頭辞。主キーは `uuid`。すべての表に `created_at / created_by / updated_at`。

### 5-1 組織・権限
| テーブル | 主な列 | 説明 |
|---|---|---|
| `mn_clinics` | id, code（hirakata, taguchiyama, tsuda, katano, ibaraki, owada, korien）, name, sort | 7院。院IDは既存 `lib/pin-auth.js` と同じ |
| `mn_members` | id, clinic_staff_id（既存台帳との紐づけ）, auth_uid, name, employment_type（正社員/パート・アルバイト）, joined_on, retired_on, is_active | スタッフ |
| `mn_assignments` | member_id, clinic_id（社長・GMは null＝全社）, position（president/gm/bm/manager/sub_manager/chief/staff/newcomer）, is_primary, valid_from, valid_to | 所属・役職（異動・兼務） |
| `mn_bm_areas` | bm_member_id, clinic_id, valid_from, valid_to | BMの担当院 |
| `mn_delegations` | from_member_id, to_member_id, permission, valid_from, valid_to, reason | 代理承認 |

### 5-2 ルール・マニュアル
| テーブル | 主な列 | 説明 |
|---|---|---|
| `mn_docs` | id, code（RULE-ATT-001 など）, kind（rule/staff_manual/manager_manual/training）, category（14種）, title, importance（A/B/C）, target_positions[], target_clinics[]（空＝全院）, status, current_version_id, source（google_doc/proposal）, source_ref（分析書の S01 など） | ルール・マニュアル項目 |
| `mn_doc_versions` | id, doc_id, version_no, body（本文）, original_text（原文。取込時のまま変更不可）, sections（院長マニュアルの9欄 jsonb）, effective_on, change_summary, requires_reack | 版。公開後は変更不可、改訂は新しい版を作る |
| `mn_doc_reviews` | version_id, step（gm_review/president_approval）, reviewer_id, decision（approve/return/hold_legal）, comment, decided_at, via_delegation_of | 承認の記録 |
| `mn_doc_conflicts` | doc_id, conflicting_doc_id, note, status（open/resolved）, resolved_by | 原文と新規提案の矛盾。open の間は提案側を公開不可 |
| `mn_doc_links` | from_doc_id, to_doc_id or form_type, relation（related_manual/related_form） | 関連マニュアル・関連申請 |
| `mn_doc_acks` | version_id, member_id, acked_at | 確認済みスタッフ（版ごと） |
| `mn_search_synonyms` | term, canonical | 検索の言い換え |

**状態（status）の流れ**：`draft（下書き）→ gm_review（GM確認待ち）→ president_approval（社長承認待ち）→ published（公開）→ archived（廃止）`。どこからでも `legal_hold（法令確認待ち）` と `returned（差し戻し）` へ。原文取込はすべて `draft` から。
改訂で `requires_reack = true` の版が公開されたら、対象スタッフ全員に通知し、`mn_doc_acks` が付くまで「未確認」と表示する。

### 5-3 申請・承認・残数
| テーブル | 主な列 | 説明 |
|---|---|---|
| `mn_requests` | id, type（paid_leave/day_swap/comp_day/part_time_work）, applicant_id, clinic_id, status, payload（jsonb：日付・時間帯・パターン等、zodで検査）, submitted_at, is_urgent | 申請 |
| `mn_request_events` | request_id, event（submitted/shift_checked/gm_consulted/approved/rejected/change_requested/changed/cancelled/reclassified）, actor_id, comment, reject_reason, before, after, at, via_delegation_of | 申請の履歴（追加のみ） |
| `mn_paid_leave_grants` | member_id, granted_on, days, expires_on（付与から2年）, basis | 有給の付与 |
| `mn_paid_leave_uses` | member_id, request_id, date, unit（全日/半日）, grant_id | 有給の取得（古い付与から消化） |
| `mn_holiday_swaps` | member_id, kind（day_swap＝事前の振替／comp_day＝事後の代休）, work_date, holiday_date, designated_at, status, request_id | 振替休日・代休。勤務実績と休日区分を記録。区分の変更は `mn_request_events.reclassified` に前後の値つきで残し、権限者の確認が必要 |

- 有給は**届出**として作る：スタッフが提出 → 院長がシフト影響を確認（コメントのみ）→ 社長が「受理」または「時季変更の相談」。理由欄は任意、理由による却下の選択肢は作らない。緊急時（前日・当日）は「GMに相談」ボタンで GM に通知。年5日に届いていない人を社長・院長に表示。
- 振替休日の残数不足は警告（提出はできるが、承認者に警告を表示）。
- アルバイト申請の3パターン（シフト作成前／急なヘルプ／繁忙時間帯）は `payload.pattern` で区別。**振替休日→アルバイト勤務への変更は、事前申請＋社長承認がないと登録できない**ようにする。ただし運用開始は法令確認（分析書 §4-11）が終わってから。
- 共通：申請日時・承認者・承認日時・却下理由・変更履歴はすべて `mn_request_events` に残る。

## 6. 承認の前に決めていただきたいこと

1. **ログイン方法**：（推奨）社長・GM・BM・院長はメールアドレス（Supabase Auth）、スタッフは既存の「院ID＋院PASS＋個人PASS」を使う。既存の仕組みを使えば新しいアカウント配布が不要。代わりに、スタッフもメールアドレスにそろえる方法もある
2. **組織の割り当て**：GM・BM は誰で、BM はどの院の担当か。原文の「マネージャー」は GM と BM のどちらか。副院長・チーフに議事録の代理入力やKPI入力を許可するか
3. **「アルバイト申請」の意味**：社員が休日に追加で働くことか、パート・アルバイト雇用の人の勤務申請か（法令の扱いが変わる）
4. **法令確認の担当**：分析書 §4 の項目（特に §4-2 労働時間、§4-3 交通事故トーク、§4-4 保険、§4-11 有給・アルバイト）を確認してもらう社労士・弁護士の方はいるか
5. **KPIの入力元**：毎日の手入力にするか、既存の売上・新患スプレッドシートから自動で取り込むか（取り込める項目が多いほど院長の手間が減る）
6. **院長LINEとの関係**：初期版はシステムと院長LINEを併用し、議事録・申請から順にシステムへ移す、でよいか
