# 本番の導入手順（PHASE 10）

**この手順の実行（本番のデータベースの変更・本番公開・実データの登録）は、社長の明示的な承認をいただいてから行う。**
テストの結果は [test-results.md](./test-results.md)、受け入れテストは [acceptance-checklist.md](./acceptance-checklist.md)。

## 1. 承認をいただく前に決めること

| 項目 | 内容 | 状態 |
|---|---|---|
| 本番への反映の承認 | 本番の Supabase（既存プロジェクト）に新システムの領域（`mgmt`）を作り、POS の会議・行動計画の表に列を足す | **承認待ち** |
| 導入日・全7院同時導入 | 院長・スタッフへの案内日、ID・PASS配布日 | 未定 |

| 初期規定 001〜005 の本文 | 社長・GM が本文を確認し、承認・公開する（初期案のまま公開も可） | 確認待ち |
| 有給取得率の定義（Q-19） | 暫定の定義で表示中 | 確認待ち |
| 再ログインの時間 | 初期値 12 時間（`REAUTH_HOURS`） | 確認待ち |
| バックアップの保存先（Q-28） | 無料プランには自動バックアップが無い。週1回のエクスポートの保存先 | 未定 |
| POS の店舗表への院の追加（Q-27） | 香里園駅前院・茨木院以外の5院は POS に無い。新システムだけで会議を管理するなら追加は不要 | 今回は追加しない（新システムだけで管理） |

## 2. 導入の当日の手順

作業者：開発担当（Claude）＋社長の立ち会い。所要：約1〜2時間（データの取り込みを除く）。

### 2.1 バックアップ
1. 本番の Supabase のデータベースを丸ごと書き出す（Supabase の画面の Database → Backups、または `supabase db dump`）。
2. 書き出したファイルを会社の保存先に置き、日付を記録する。

### 2.2 データベース（本番の Supabase）
1. `management/supabase/migrations` の 14 個のファイルを、**番号の順に**適用する。
   - 9 番（`20261110000009_meetings.sql`）は POS の `public.meetings`・`public.action_items` に**列を足すだけ**（既存の列・データ・権限は変えない）。既存の会議は「対象外（移行前）」になる。
   - `supabase/tests/pos-stub.sql` は**本番には適用しない**（検証用の POS の表の再現）。
2. 初期マスタ `management/supabase/seed/0001_master.sql`（役職・権限・7院）と `0002_rules.sql`（初期規定 001〜005 の初期案）を適用する。
3. `management/supabase/production/01_link_pos_stores.sql`：POS の店舗と紐づける（適用前に POS の店舗の番号と院名を確認）。
4. Supabase の画面の Settings → API → **Exposed schemas に `mgmt` を追加**する（新システムの画面から関数を呼べるようにする）。
5. `management/supabase/production/02_first_president_template.sql` の `<…>` を社長本人の値に置き換えて実行し、最初の社長を登録する（社長が POS で使っている ID にプロフィールを紐づける）。
6. 確認：
   - Supabase のセキュリティ診断で、新しい「警告」が増えていないこと。
   - POS の画面（香里園駅前院）で、会議・行動計画の一覧が今までどおり表示・登録できること（T-18）。

### 2.3 画面（Vercel）
1. Vercel に新しいプロジェクトを作る：リポジトリはこのリポジトリ、**Root Directory を `management`** にする（既存の公開ページのプロジェクトとは別。既存側は `.vercelignore` で `management/` を除いている）。
2. 環境変数を設定する（値はリポジトリに書かない）：

| 名前 | 値 |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | 本番の Supabase の URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 本番の公開キー（publishable） |
| `SUPABASE_SERVICE_ROLE_KEY` | 本番のサービスロールキー（**サーバー専用**。ID・PASSの発行と定期処理だけに使う） |
| `LOGIN_ID_DOMAIN` | `ando.jp`（POS と同じ） |
| `CRON_SECRET` | 長いランダムな文字列（定期処理の合言葉） |
| `REAUTH_HOURS` | 省略時 12（承認などの前に再ログインを求める時間） |

3. デプロイし、`management/vercel.json` の定期処理（毎日 9:00 JST の `/api/cron/daily`）が Vercel の Cron Jobs に表示されることを確認する。
4. 確認：社長がログインし、社長ダッシュボード・スタッフ管理が開けること。翌朝、社長ダッシュボードの「毎日の自動処理」が「正常に終了」になっていること。

### 2.4 実データの登録（社長が画面で行う）
1. `/admin/import` でスタッフの台帳（CSV）を取り込み、ID・PASSを発行する（POS で使っている ID はそのアカウントに紐づく）。院長・GM・BM の役職と担当エリアを設定する。
2. `/admin/import` で有給・振休の初期残数（付与ごとに1行の CSV：Q-5）を取り込む。取り込み結果を社長・各院長が確認する（取り消しも可能）。
3. `/admin/stores` でシフト確定の基準日（20日）を確認する。
4. 社内規定 001〜005 を確認し、承認・公開する（スタッフに通知され、確認をお願いする）。
5. 1名で確認：
   - 発行した ID・PASS で新システムと POS の両方にログインできること（T-17）。
   - 有給の申請 → 社長の承認 → 残数の反映。

### 2.5 案内
- ID・PASS は1人ずつ手渡し（初回ログイン時に PASS の変更を求められる）。
- 院長向け：振休の承認、会議の登録と議事録の提出（開催日の3日後の23:59まで）、アルバイト勤務の申請。
- スタッフ向け：休暇の申請、タスクの更新、規定の確認。

## 3. 問題があったときの戻し方

| 状況 | 対応 |
|---|---|
| 画面の不具合 | Vercel で直前のデプロイに戻す（Instant Rollback）。データはそのまま |
| データの誤り（取り込みなど） | CSV の取り込みは画面から取り消せる。残数は社長が理由つきで修正（履歴が残る） |
| 新システムをいったん止める | Vercel のプロジェクトを止める。POS は影響を受けない |
| 新システムをやめる | `management/supabase/production/99_rollback.sql`（**データが消える**。バックアップの後、社長の承認を得て実行）。POS の表は元の列だけに戻り、POS の画面はそのまま動く（自動テストで確認済み） |

## 4. 運用

- 毎日 9:00：自動処理（取得済みの反映・各種の期限の通知・月曜は年5日）。結果は社長ダッシュボードに表示。失敗していたら開発担当に連絡。
- 週1回：バックアップ（Q-28 の保存先が決まりしだい手順を追記）。
- 退職・異動：社長がスタッフ管理で退職処理・所属の終了を行う。承認する院長がいなくなった振休は、社長・GMに「承認者不在」が届く。
- 4月（年度の初め）：祝日の表の更新（内閣府の祝日 CSV）。
