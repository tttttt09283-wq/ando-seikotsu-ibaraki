## 3. セキュリティ検証（test-plan.md §6）

| 項目 | 結果 | 内容 |
|---|---|---|
| RLS網羅 | 合格 | mgmt の全テーブルで RLS が有効（自動テスト）。ポリシーの無い表は「関数からだけ読み書きする表」（議事録・規定・定期処理の記録など）で、ログイン中の利用者には表の権限自体を与えていない |
| 公開の鍵（anon） | 合格 | mgmt の表・関数を anon は一切使えない（自動テスト・検証用 Supabase の権限表で確認） |
| SECURITY DEFINER の関数 | 合格 | すべて `search_path` を固定（自動テスト） |
| 直接更新の禁止 | 合格 | 申請・承認・取得・規定の表は社長でも直接は変えられない。直接書ける表はマスタ・取り込み・付与の10表だけで、RLS で社長の権限に限っている |
| 監査ログ | 合格 | `audit_logs`・`approval_events` は誰も（データベースの管理者でも）変更・削除できない |
| 退職者 | 合格 | 退職・停止のアカウントは何も見えない。**院長の退職・異動で承認する人がいなくなった振休は、社長・GMに「承認者不在」を通知**（PHASE 10 で追加） |
| 入力値 | 合格 | 範囲外・長すぎる値は DB が拒否。HTML は文字として保存し、画面では React がエスケープして表示 |
| サービスロールキー | 合格 | ブラウザに送られるファイルに含まれない（ビルド結果を検索）。サーバー専用のファイルにだけある |
| 承認者の本人確認 | 合格 | 承認・差戻し・却下・規定の公開・残数の修正・CSV取り込み・ID/PASSの発行の前に、最後のPASSでのログインから **12時間**（`REAUTH_HOURS` で変更可。時間は要確認）を超えていたら再ログインを求める。画面で確認：再ログイン後は元の画面に戻り、承認できる |
| 通知の重複 | 合格 | 毎日の処理を2回動かしても、通知は1回（自動テスト・検証用 Supabase） |
| 定期処理の呼び出し | 合格 | `/api/cron/daily` は合言葉（`CRON_SECRET`）が無いと 401。定期処理の関数はサービスロールだけが呼べる |

Supabase のセキュリティ診断（検証用プロジェクト）で残った指摘：
- 「RLS は有効だがポリシーが無い表」（情報）：上のとおり意図した設計（関数からだけ使う表）。
- `public.is_staff()` を anon が呼べる（警告）：**既存のPOSの関数**（検証用には同じ形で再現）。新システムでは変更していない。POS 側で対応するかは別途ご判断。
- 漏えいしたPASSの確認（HaveIBeenPwned）が無効（警告）：Supabase Auth の設定。有料プランの機能のため、無料で運用する方針（Q-26）では有効にできない場合がある。
