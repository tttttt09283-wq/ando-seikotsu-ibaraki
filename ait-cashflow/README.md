# A.I.T Cash Flow

従業員1〜10名の小規模企業の経営者が、**現在の現預金・入金予定・支払予定・将来の資金不足リスク**をひと目で把握するためのWebアプリです。

- 設計書：[docs/PLAN.md](docs/PLAN.md)（アーキテクチャ・画面一覧・ER図・計算仕様・開発タスク・セキュリティ）
- 技術：Next.js 16（App Router）・TypeScript・Tailwind CSS v4・shadcn/ui 方式のUI部品・Recharts・Supabase（PostgreSQL / Auth / RLS）・Zod・Vitest
- 日本語UI・日本円・Asia/Tokyo。スマホ優先

このフォルダ（`ait-cashflow/`）は独立したアプリです。リポジトリ内のほかのアプリ（ルートのHTML・`api/`・`body-check/`・`ait-company-os/`・`enejoy-hand-ai/`）には手を入れていません。

## 起動方法

### 1. デモモード（Supabase なし・すぐ見られる）

```bash
cd ait-cashflow
npm install
npm run dev
```

http://localhost:3002 を開きます。ログインなしで、**架空のデモデータ**（画面上部に常に「デモモード」と表示）で動きます。データはサーバーのメモリ上だけにあり、再起動や「最初の状態に戻す」で元に戻ります。**実際の企業データは入力しないでください。**

### 2. 本番モード（Supabase）

> 以下は Supabase のアカウント・プロジェクトが必要です。**作成・設定はご本人の判断で行ってください**（このリポジトリには鍵や認証情報を含めていません）。

1. Supabase でプロジェクトを作る（リージョンは Tokyo（ap-northeast-1）を推奨）
2. **SQL Editor** で `supabase/migrations/20261019000000_init.sql` の内容を実行する
   （Supabase CLI を使う場合は `supabase link` のあと `supabase db push`）
3. **Authentication → Providers → Email**：Email を有効、「Confirm email」を ON
4. **Authentication → URL Configuration**：
   - Site URL：`http://localhost:3002`（本番は公開URL）
   - Redirect URLs：`http://localhost:3002/auth/confirm`（本番URLの `/auth/confirm` も追加）
5. **Authentication → Email Templates → Confirm signup** のリンクを次に変更：
   `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=email`
6. `.env.example` を `.env.local` にコピーし、**Project URL** と **publishable key（anon key）** を入れる
   （**service_role / secret key は使いません。入れないでください**）
7. `npm run dev` → `/signup` で登録 → 確認メールのリンク → 企業を作成（作った人がオーナー）

本番ビルド：`npm run build && npm start`（ポート 3002）。Vercel 等にデプロイする場合は、同じ環境変数をホスティング側に設定し、Root Directory を `ait-cashflow` にします。

## 既知の制限

- **Supabase モードは実際の Supabase プロジェクトでの動作確認がまだです**（この開発環境から Supabase に接続できないため）。DB部分は実際の PostgreSQL（PGlite・PostgreSQL 16）でマイグレーションとRLSを検証済み、アプリ側は型チェックとデモモードでの画面操作まで確認済みです
- 祝日は考慮していません（土日だけ前後の平日にずらします）
- レート制限はサーバーのメモリ上で数えます（複数台構成では Redis 等に置き換えが必要）
- 一度に読み込む取引は、予定すべて＋直近400日の確定・取消（各5,000件まで）
- 繰返しの回で予定日を過ぎたまま確定していないものは、予測に含めません（「入出金一覧」で確定するか設定を見直してください）
- デモモードのデータはサーバーのメモリ上だけ（再起動で消えます）

## セキュリティ

- **企業ごとのデータ分離**：全業務テーブルに `organization_id`。Supabase の RLS で「その企業のメンバーだけ」が読め、「オーナー・経理担当だけ」が書ける。子テーブルは `(organization_id, id)` の複合外部キーで他社のデータを参照できない
- **アプリでも二重に確認**：Server Action ごとに、ログイン・メンバーシップ・権限・レート制限・入力検証を行う
- **シークレット**：環境変数で管理し、`.env.example` だけをコミット。サービスロールキーは使わない
- **ログ**：口座番号は下4桁のみ保存。エラーログに金額・取引先・トークンを出さない
- **監査ログ**：すべての追加・変更・削除をトリガーで `audit_logs` に記録（誰が・いつ・変更前後）。利用者は書き込めない
- **CSVの数式インジェクション**：`= + - @` などで始まる値を無害化する関数を用意（フェーズ3の取込・出力で使用）
- **AI**（フェーズ4）：計算の根拠にしない。同意取得後、検証済みの集計値のみを送り、下書きだけを作る。振込・支払・仕訳の自動実行はしない

## バックアップと復元方針

| 項目 | 方針 |
|---|---|
| 自動バックアップ | Supabase の日次バックアップ（Pro プラン以上は保持期間あり）。重要度に応じて PITR（任意の時点への復元）を有効化 |
| 手動バックアップ | 月次・大きな変更の前に `pg_dump`（Supabase の接続文字列を使用）で取得し、暗号化して社外の安全な場所に保管。バックアップファイルには口座・取引データが含まれるため取り扱いに注意 |
| 復元手順 | ①新しいプロジェクト（または同じプロジェクト）に `supabase/migrations` を適用 → ②`pg_restore`／SQL で復元 → ③Auth のユーザーは Supabase のバックアップから復元（Auth を含めて復元する場合はダッシュボードの Restore を使う） |
| 復元後の確認 | 企業・メンバー・口座の件数、口座ごとの最新の基準残高、ダッシュボードの現在残高が復元前の記録と一致するか、RLSが有効か（`select relrowsecurity from pg_class`） |
| 復元テスト | 半年に1回、検証用プロジェクトに復元して上の確認を行う |
